# Data Sources

Provenance and licensing for every piece of geodata and metadata used by this game.
Each entry records where the data came from, how it is processed, and under what licence
it may be redistributed.

**Status:** sections 1, 2, 5, 6 and 7 cover the like-for-like Bundesland quiz specified
in `.scratch/bundesland-quiz/spec.md`, and are vendored: `data/bundeslaender.topo.json`,
`data/kulisse.topo.json`, `data/bundeslaender.json` and `wappen/de-*.svg`. The geometry
and the Landeswappen are regenerated by hand with `tools/vendor-germany-data.sh`; the
metadata is hand-curated (§7). `tools/data-review.html` shows all of it in a browser
(`make run`, then <http://localhost:8000/tools/data-review.html>). Sections 3 and 4 (rivers, lakes and cities) are for
the Gewässer & Städte modes (`.scratch/gewaesser-staedte/spec.md`) and are vendored too:
`data/gewaesser.topo.json` and `data/staedte.json` (OpenStreetMap, **ODbL**, regenerated by hand with
`tools/vendor-landmark-data.sh`), and the hand-curated `data/landmarks.json` and
`data/landmark-aliases.json`. No mode draws them yet.

**Keying:** all data is keyed by **ISO 3166-2 subdivision code** (`DE-BW`, `DE-BY`, …),
per the spec. Sources that use other schemes are normalised on the way in.

**No build step, no npm.** The app stays openable as a static page — the project's
"no build process, no npm required" property is preserved. The processing recipes below
are one-off data-preparation steps, run by hand only when data needs regenerating (via
`npx` or a system install of the tool, never as a project dependency); their committed
JSON output is what the app fetches at runtime. The world quiz this game replaced
handled its generated click-target data the same way (a one-off script whose output was
committed), and it keeps the tooling off the critical path for running or changing the
game.

## 1. Germany outline

Not fetched separately. Derived by dissolving the 16 Bundesland polygons from §2 and
buffering the result by 5 km.

| | |
|---|---|
| **Method** | `topojson-client`'s `merge()` over the 16 polygons, then `mapshaper -buffer 5km` |
| **Used for** | Clipping the rivers (§3) to Germany. Lakes are kept whole and cities are points, so neither is clipped |
| **Licence** | Inherits Eurostat GISCO terms from §2 |

The 5 km buffer means rivers that cross or follow the border (the Rhein, the Oder, the Inn)
are retained slightly beyond the national boundary rather than being cut flush at it. In
`tools/vendor-landmark-data.sh` the dissolve and buffer are both mapshaper
(`-dissolve`, then `-buffer 5km`) over `data/bundeslaender.topo.json`.

## 2. Bundesländer boundaries

The 16 federal states — the core geometry for every game mode.

| | |
|---|---|
| **Source** | Eurostat GISCO, NUTS-1 regions, 1:3M scale, EPSG:4326, 2021 release |
| **URL** | <https://gisco-services.ec.europa.eu/distribution/v2/nuts/geojson/NUTS_RG_03M_2021_4326_LEVL_1.geojson> |
| **Filter** | `CNTR_CODE=DE` — yields exactly 16 features |
| **Processing** | Filter to Germany → map NUTS-1 code to ISO 3166-2 key → `mapshaper -explode -simplify 100% keep-shapes -clean -dissolve` → TopoJSON (unquantized, 4 decimals) — see "Processing notes" below |
| **Output** | `data/bundeslaender.topo.json` — object `bundeslaender`, 16 geometries, each `id` = ISO 3166-2 key (~64 KB) |
| **Script** | `tools/vendor-germany-data.sh` (mapshaper 0.7.70 via `npx`; downloads cached in `tools/.cache/`, removed by `make clean`) |
| **Licence** | Eurostat GISCO terms, **non-commercial use only, with attribution** — see "Attribution" below |

**Attribution.** GISCO grants "the non-exclusive and not transferable right to use and
process the Eurostat/GISCO geographical data" on condition that "the data will not be
used for commercial purposes" and "the source will be acknowledged. A copyright notice,
as specified below, will have to be visible on any printed or electronic publication
using the data downloaded from this page." The required notice is:

> EN: © EuroGeographics for the administrative boundaries
> DE: © EuroGeographics bezüglich der Verwaltungsgrenzen

The game's UI is German, so the German wording applies; it must be **visible in the app**
wherever the map is shown (e.g. a footer line
`Kartengrundlage: © EuroGeographics bezüglich der Verwaltungsgrenzen`). Terms from the
GISCO geodata pages (<https://ec.europa.eu/eurostat/web/gisco/geodata>, the terms appear
in the dataset download dialog); the wording above was taken from the verbatim quotation
in the eurostat R package documentation
(<https://ropengov.github.io/eurostat/reference/get_eurostat_geospatial.html>) because the
live GISCO page renders the terms dynamically and could not be captured when vendoring
(September 2026). Commercial use would need a licence from EuroGeographics.

**This app qualifies:** it is a non-commercial educational app (confirmed by the
maintainer, 2026-09-30), so the GISCO terms are met as long as the notice above is shown.

**Processing notes.**

- **Scale: 1:3M, kept whole.** The data was first vendored at GISCO 1:10M, which is so
  generalised that the Stadtstaaten looked crude at game zoom (Berlin 20 vertices,
  Bremen 18, Hamburg 23); the recipe's original `-simplify 10%` of it turned Berlin and
  Hamburg into triangles. 1:3M (Berlin 66, Bremen 59, Hamburg 69, Saarland 110) was
  compared side by side in `tools/data-review.html` and chosen (2026-09-30), for both
  layers, with no further simplification. Measured alternatives, Bundesländer + Kulisse:
  10M 21 + 138 KB; **03M 64 + 542 KB**; 01M at 40% 135 KB + 1.0 MB; 01M whole
  244 KB + 2.8 MB. The script's `SCALE`/`SIMPLIFY` knobs stay for experiments.
- **Possible later refinement (not done):** finer Bundesländer only (GISCO 1:1M, or BKG
  VG250 under Datenlizenz Deutschland) over a coarser Kulisse. Almost all the bytes are
  in the Kulisse, so this buys detail cheaply, but the two layers would no longer share
  one border; the idea is to hide the mismatch by drawing a Germany-shaped underlay in
  the Kulisse colour beneath the Bundesländer. Deferred by the maintainer: 1:3M everywhere
  is good enough for now.
- **One shared topology with the Kulisse (§6).** Both GISCO files are imported into one
  mapshaper dataset (`combine-files snap`), so the German land border is a single set of
  arcs used by both layers, and both files are written unquantized at 4 decimal places.
  Checked after generation: every German outer-border vertex on a land border is also a
  Kulisse vertex (1:3M: 978 shared exactly; the only unshared inland points are on the
  Jadebusen shore, i.e. coastline).

## 3. Rivers and lakes

The Gewässer & Städte modes' 18 rivers (10 pool, 8 background) and 11 lakes (7 pool,
4 background). Not drawn by any mode yet.

| | |
|---|---|
| **Source** | OpenStreetMap, via the Overpass API (<https://overpass-api.de/api/interpreter>), downloaded 2026-10-01 |
| **Query key** | **Wikidata ID, pinned to OSM ids** (spec "The feature pool" has the table; the script holds the same rows). Name-based queries return wrong features — there is more than one "Oder" |
| **Processing** | Pin → rivers: `type=waterway` relation, members with role `main_stream` or none, `out geom(47.0,5.5,55.3,15.3)` → clip to the buffered outline (§1); lakes: `natural=water` relation or way, rings stitched from the outer/inner members, **not clipped** → `mapshaper -simplify interval=200m keep-shapes` → TopoJSON unquantized at 4 decimals |
| **Output** | `data/gewaesser.topo.json` — objects `rivers` (18) and `lakes` (11), each geometry `id` = feature id (`river-rhein`, `lake-bodensee`, …). **217 KB, 64 KB gzipped** |
| **Script** | `tools/vendor-landmark-data.sh` (mapshaper 0.7.70 via `npx`; Overpass responses cached in `tools/.cache/landmarks/`, removed by `make clean`) |
| **Licence** | © OpenStreetMap contributors, **ODbL 1.0** — <https://www.openstreetmap.org/copyright>, <https://opendatacommons.org/licenses/odbl/1-0/> |

**Pinning.** For every feature the script asks Overpass for every relation (lakes: and
way; cities: `place=city` node) carrying its Wikidata tag, and **fails** unless the answer
is exactly the pinned objects plus the known traps listed for that row. Only the pinned
objects' geometry is then fetched. The traps, all carrying the same Wikidata id as the
feature, re-checked 2026-10-01:

| Feature | Trap | Why it is dropped |
|---|---|---|
| Aller (Q1967803) | relations 15004441, 15004494 "Aller Schleuse" | Lock channels, themselves `type=waterway`: a type filter alone would merge them |
| Main (Q1670) | relation 6274126 | Riverbank multipolygon (`natural=water`) |
| Inn (Q14369) | relation 4621343 | Riverbank multipolygon (`natural=water`) |
| Schweriner See (Q311217) | relation 282711 | `type=site` relation for the lake |
| (Saar, not in the pool) | relation 5441202 "Weiße Saar" | Would need listing if the Saar is added |

The Schweriner See is the union of the Außensee (relation 1104680, which carries the
Wikidata tag) and the Innensee (relation 21142, no Wikidata tag, **pinned by OSM id**).
The failure path was exercised when vendoring: with the Aller's traps un-pinned, the
script stops with `river-aller (Q1967803): Overpass returned [relation/123707,
relation/15004441, relation/15004494], pinned [relation/123707]; unexpected: … "Aller
Schleuse" type=waterway …` and writes nothing. River *ways* carry the river's Wikidata
tag by the hundred, so they are never part of the pin query.

**Processing notes.**

- **Main stream only.** `side_stream`, `tributary`, `distributary` and `spring` members
  are dropped, so there are no Altrhein arms. Overpass's bbox-truncated geometry has
  `null` for nodes outside the box; lines are split there.
- **Lakes are not clipped**: the 5 km clip cut a straight line through the Swiss end of the
  Bodensee, and every other lake lies wholly in Germany. The Bodensee is whole
  (533 km² as vendored; 536 km² published). Lakes are dissolved by id, so the two Schweriner
  See relations are one feature (two parts).
- **Simplify by interval, not percentage** (200 m): OSM vertex density varies too much
  between rivers for a percentage to mean anything, and 200 m keeps full detail at the
  6× maximum zoom (about 160 m per CSS px).
- **Robustness.** A busy Overpass answers HTTP 200 with an HTML error page (and a timed-out
  query can answer 200 with JSON whose `remark` reports an error), so the script checks
  that the body is JSON with no error remark, retries with a 30/60/90 … s back-off (the
  2026-10-01 run needed it after HTTP 429 and 504 answers), sends batches of at most six
  features, and a descriptive User-Agent. Cache file names carry a checksum of the query,
  so an edited query is never answered from a stale download.
- **Checks** (`test/data.test.mjs`): ids agree with `data/landmarks.json`, every river
  lies inside Germany's bounds + 5 km, each lake's centroid lies in one of its
  `bundeslaender` (the Bodensee's lies in open Obersee water no GISCO polygon covers, so
  the nearest Bundesland, BW, is checked instead).

**ODbL is share-alike.** The two OSM files are a derivative database and are offered
under ODbL 1.0 only, kept in their own files and never merged into the GISCO topology;
`LICENSE` lists them under "Third-party material", and the app credits OpenStreetMap on
the Einstellungen screen. See
[ADR 0002](docs/adr/0002-osm-data-odbl-separate-files.md) for the decision and the credit
placement.

**Natural Earth was evaluated and rejected**: see
[ADR 0001](docs/adr/0001-natural-earth-rejected-for-hydrography.md). This section first
said "the Rhein is cut off, the Donau's German stretch is absent"; that does not reproduce
against Natural Earth 5.0.0 (re-checked 2026-09-30). The real problems are mislabelled
extents (its "Weser" includes the Werra, its "Aller" the Leine) and rivers missing
entirely (Havel, Werra, Lahn, Lech). The ADR has the measurements.

## 4. Cities

The 24 city points: 8 Städte and the 16 Landeshauptstädte, all in the pool.

| | |
|---|---|
| **Source** | OpenStreetMap via Overpass — same pipeline and date as §3: one `place=city` node per Wikidata id, pinned to its node id |
| **Output** | `data/staedte.json` — GeoJSON FeatureCollection of 24 points, `id` = feature id (`city-koeln`, …), coordinates at 4 decimals. **2.8 KB, 0.5 KB gzipped** |
| **Licence** | © OpenStreetMap contributors, ODbL 1.0 — as §3, share-alike |

The pin query is restricted to `place=city` nodes (the spec's rule): unrestricted, it also
returns stray objects; on 2026-10-01 a Stuttgart parking-ticket machine (node 12288961790)
carried Stuttgart's Wikidata id.

**Names come from the curated `data/landmarks.json`, not from OSM tags** — OSM's own
primary names include "Odra", "Danube" and "Lužická Nisa". Each Landeshauptstadt's name
equals `capital` in `data/bundeslaender.json` (a test enforces it).

### Wappengesetz caveat — read before use

**German law restricts the use of official state insignia.** Each Bundesland's
Wappengesetz (state insignia law) governs who may use its Landeswappen and how, chiefly
to prevent unauthorised use that implies official or governmental status.

Vendoring these sixteen files here is for a **private, non-official learning app**: no
commercial use, no claim of official status, and no implication of endorsement by any
Bundesland or its government. This is not legal advice about where that line sits for
other uses — it is a note for a future maintainer about why the files are here and under
what understanding.

## 6. Kulisse (neighbouring countries)

The muted, non-interactive land around Germany (spec: "The Kulisse layer").

| | |
|---|---|
| **Source** | Eurostat GISCO, Countries 2020, 1:3M, EPSG:4326 — same provider and scale as §2 |
| **URL** | <https://gisco-services.ec.europa.eu/distribution/v2/countries/geojson/CNTR_RG_03M_2020_4326.geojson> |
| **Filter** | Drop `CNTR_ID=DE` (Germany is §2), then clip to the box lon −12…34°E, lat 40…62°N |
| **Processing** | Imported into the same mapshaper dataset as §2 (`combine-files snap`), `-clip bbox=-12,40,34,62`, same simplify/clean, TopoJSON unquantized at 4 decimals |
| **Output** | `data/kulisse.topo.json` — object `kulisse`, one geometry per country, `id` = GISCO `CNTR_ID` (~542 KB, ~184 KB gzipped) |
| **Licence** | Eurostat GISCO terms, as §2 — non-commercial, the same EuroGeographics notice |

**Why this box.** Germany spans about 5.9–15.0°E and 47.3–55.1°N. On a wide screen the
fitted Germany view letterboxes horizontally, and the conic projection slants the box's
meridian edges, so the box reaches far beyond Germany. A first try at −2…24°E showed its
slanted edges inside the margins of a 21:9 view; the wider box fills both 16:9 and 21:9
(checked in `tools/data-review.html` at 1920×1080 and 2560×1080: the margins show
UK/France and Poland/Slovakia/Hungary at 16:9, Ireland and Belarus/Ukraine/Romania at
21:9, or genuine sea). The neighbours AT, BE, CH, CZ, DK, FR, LU, NL, PL are all whole
inside it.

**No gaps against the Bundesländer.** Because both layers come out of one topology, the
German land border is literally the same vertices in both files (checked: every
land-border vertex of the dissolved Bundesländer outline is a Kulisse vertex). GISCO's
2020 country outline and 2021 NUTS outline are the same EuroGeographics-derived line; at
1:3M mapshaper's `snap` joins 126 near-coincident points, and a 6× zoom along the
French/Luxembourg border in `tools/data-review.html` shows no slivers or gaps. The Kulisse contains no German territory (checked by
`test/data.test.mjs`).
